# 全项目性能与耗电审查

日期：2026-11-07。基线提交：`cbebd80`。审查覆盖启动、Compose 订阅、搜索、扫描、封面、普通与加密阅读、数据库写入、后台任务及构建配置。

## 实施契约

优先消除重复 I/O、重复解密、重复解码、轮询唤醒和离开页面后继续执行的预取。保留加密认证、撤销、完整校验、进度保存和 SAF 权限边界。不降低口令 KDF 成本，不增加后台定时任务，不更改视觉布局。

拟修改 `core:vault` 的随机读取、`app` 的 FileVaultStore/LibraryRepository/DocumentRenderSession/AsterViewModel，以及页面 Flow 的生命周期订阅。新增关键算法与并发回归测试。执行 app/database/vault 全量单测、Lint、debug 打包、Release R8，并在当前 API35 模拟器运行隔离设备测试、启动及后台检查。

## 已确认的根因

1. 加密 Reader 的每次小读取都重新解密整个 1 MiB 块。ZIP 索引、图片流和 PDF 小块随机读取会重复消耗 CPU 和分配内存。
2. `committedIds()` 每次调用都枚举磁盘目录；批注过滤对每条批注重复调用，放大为批注数乘保险库文件数的 I/O。部分 Flow 变换由主线程收集。
3. 渲染与预取只在解码前检查缓存，并发请求可能重复解码同一页。ZIP/图片目录没有并发解码总量限制。
4. 切换/关闭阅读来源以 5 ms 轮询等待在途工作，产生无意义唤醒。
5. 每次翻页在 ViewModel 启动独立预取任务；新翻页和离开阅读不会取消旧预取，后台可能重新打开已关闭来源。
6. 搜索、详情和统计仍有非生命周期订阅，页面留在后台时继续收集。
7. 书库的 `sample(150)` 在订阅期间维护周期计时器，即使数据没有变化仍周期唤醒。改为 `conflate + transform`：收到数据后发布一次，再合并 150 ms 内的突发更新，空闲时无周期计时器。
8. 加密归档页名校验使用 List.contains，形成平方级查找；7z/RAR 每次取页重新线性查找条目。改用 Set 与一次构建的条目索引，保留重复条目时原先选择首条的行为。
9. 未改变的保险库设置仍重写、校验、同步密文元数据。改为比较完整记录，未改变时跳过写入。

## 缓存与故障边界

保险库已提交 ID 在第一次读取时建立索引，每次解锁重新读取目录。元数据原子提交与索引更新由同一锁保护；更新发生在目录同步及界面发布之前。即使后续同步失败，也继续把该 ID 视为受保护内容。进程重启以磁盘元数据重建索引。锁定只移除敏感记录，不移除受保护 ID。

明文块缓存只接收认证成功的字节，不返回未认证密文。缓存命中返回该 Reader 已认证的快照；不会为检查外部修改重新读取已缓存的块。保险库对象在应用内不可原地修改；重新打开 Reader 和完整 verify 会重新认证磁盘内容。本次没有更改密文格式、密钥封装、数据库版本或用户数据。

## 尚未完成的性能目标

- 万本书库仍以完整列表供给 UI。已有 Lazy 列表、后台搜索及索引不等于数据库分页。真实大库的 Paging 与稳定 UI 投影需要单独实施并测量。
- 仓库扫描仍逐个处理文件。对大量小文件增加受控并发需真实 SAF 提供者基准；当前没有宣称达到 2–4 并发。
- 保险库解锁继续执行数据库去敏恢复与 VACUUM。跳过这一步需要持久化恢复标记，不能仅以本次是否修改数据库决定，否则崩溃恢复可能遗漏明文清理。
- Macrobenchmark/Baseline Profile 模块尚未建立；此轮没有用合成读取测试代替正式版启动、滚动或翻页 P95 验收。
- API31/35 的自动化测试不能代替 API31/API37 真机的浅深主题、平板、TalkBack 和长时间温升/耗电验收。

## 测量边界

模拟器没有真实电池，debug 耗时不代表正式版性能，也不能换算耗电百分比。隔离的固定读取工作量用于验证机制和观察前后变化；Release R8 是优化构建门禁。真实设备 Macrobenchmark、Baseline Profile、长时间能耗与温升测试另行记录，不能由静态审查替代。

依据：[Android 基准测试](https://developer.android.com/topic/performance/benchmarking/benchmarking-overview)、[生命周期协程](https://developer.android.com/topic/libraries/architecture/coroutines)。
